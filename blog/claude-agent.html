Two AIs, One Loop — Building a Self-Improving Code Agent

Describe a complex software goal in one sentence. Two Claude instances — one planner, one implementer — handle the rest, iterating until the work is done.

LLMs are remarkable at taking a bounded request and producing code. But real software engineering isn't bounded. Building a feature means planning, coding, testing, discovering you got it wrong, and trying again. It's iterative by nature.

So I wanted to see what would happen if I closed the loop myself. Not a fancy agent framework. Not a task tree. Just two Claude Code instances wired together in a cycle, with an orchestrator forwarding context and diffs between them until the job is done.

The Problem

A single prompt to an LLM gets you one pass. You describe what you want, the model writes code, and that's it. If the code is wrong, you notice and prompt again. If something subtle is off — a missed edge case, a regression somewhere else, a dependency you didn't think about — you might not notice at all.

Real development is iterative:

  • Plan. Look at the codebase, understand constraints, decide on an approach.
  • Code. Make the changes.
  • Review. Look at the diff, run the tests, check the result.
  • Refine. Fix what's wrong, go again.

Humans do this naturally. LLMs don't, unless you put them in a loop.

Two Roles, One Goal

The architecture is the simplest thing that works: two Claude Code instances, each with a different system prompt, each specialized for one part of the cycle.

The Planner is the senior tech lead. It looks at the current state of the repository — file tree, README, recent git log, the last diff produced — and decides what needs to happen next. It doesn't write code. Its job is to think, explain, and hand off a clear instruction. Its output is a natural-language directive like "add a JWT middleware at src/auth/jwt.ts that validates the access token and sets req.user. Don't touch the refresh flow yet — we'll do that next."

The Implementer is the engineer. It receives the directive from the Planner and executes it. It reads the files it needs, makes the edits, runs the tests, and reports back what it changed. It does not second-guess the plan. Its job is to make the diff happen cleanly.

Separating these two roles matters for a subtle reason. A single Claude instance asked to both plan and code has a strong bias toward writing code — even when the right move is to stop and think. Splitting the roles forces each instance to do its job fully before handing off.

Architecture

The orchestrator is a thin Python shim. It holds the conversation state for each role, forwards messages, and captures git diffs between rounds. Each iteration is a round trip through the diagram below: gather fresh context, ask the Planner what to do, hand the plan to the Implementer, collect the resulting diff, and feed the diff back to the Planner for the next iteration.

Context Gathering

Before every Planner turn, the orchestrator builds a fresh context packet. It's deliberately shallow: just enough to reason about the next step without drowning the model.

The packet includes:

  • File tree — a find-style listing of the repository, excluding node_modules, .git, and build artifacts.
  • Git log — the last 15 commits on the current branch for project memory.
  • README — verbatim, so the Planner understands the project's intent.
  • Previous diff — the unified diff the Implementer just produced, so the Planner can review what actually happened versus what was requested.

This is the feedback channel. Without it, the Planner is flying blind. With it, the Planner can catch regressions, notice when the Implementer missed a detail, and steer the next step accordingly.

The Feedback Loop

The loop is where the system earns its keep. After the Implementer reports back, the orchestrator runs git diff against the last commit and pipes that diff into the next Planner round as part of the context packet. The Planner sees exactly what changed.

That's when the interesting things start happening. The Planner notices that the Implementer added a route but forgot to register it in the router. It notices that a new function was added but no tests. It notices that an edit touched an unrelated file by accident. It writes the next directive with all of that in hand: "good work on the middleware — now wire it into src/app.ts and add a test for the invalid-token case."

A single-pass LLM couldn't do any of this. The loop makes the difference.

Running It

A full run looks like this:

python3 claude_loop.py ./my-app "Add JWT auth with refresh tokens" \
  --effort max \
  --planner-model opus \
  --impl-model opus

The key options:

  • --effort [low | medium | max] — how aggressively each Claude instance should think before responding. At max, the planner is notably more careful about edge cases.
  • --planner-model and --impl-model — pick the model for each role independently. Opus for both when the goal is tricky; Sonnet for both when speed matters; mixed when the plan is hard but the code is mechanical.
  • --max-iterations — safety cap so a confused loop doesn't run all night.
  • --timeout — per-turn timeout so a stuck subprocess doesn't hang the loop.

Termination

A loop that doesn't know when to stop is worse than no loop at all.

Termination happens in one of three ways:

  1. The Planner declares victory. After reviewing the most recent diff, if the Planner concludes the goal is achieved, it emits a GOAL COMPLETE sentinel and the orchestrator exits cleanly.
  2. The iteration cap is reached. Set with --max-iterations, this is the escape hatch for runs that get stuck in a local minimum.
  3. A turn errors. If either subprocess dies, times out, or returns a malformed response, the orchestrator writes the run log and exits so you can investigate.

In practice, the first mechanism handles roughly 80% of completed runs. The cap catches the pathological cases.

What You Can Build

I've used the loop for a range of tasks. Some it handles cleanly, others reveal the seams.

Works well

  • Well-scoped bug fixes where the failing test or error trace points at the right place.
  • Full features that are mostly mechanical — adding routes, models, and a minimal test pass.
  • Refactors where the goal can be stated precisely ("inline this helper, then delete it").
  • Test coverage campaigns — "write tests until this file is at 80%."

Works poorly

  • Open-ended architectural decisions. The Planner will commit to a direction and defend it; stepping back to reconsider is hard.
  • Anything requiring cross-repo or cross-service context. The loop only sees one repository.
  • UI work that needs human judgment about visual quality.

Get Started

The full source is on GitHub: github.com/josephgec/claude-agent.

There's no installation beyond cloning the repo and having claude in your PATH. The orchestrator is a single Python file. Fork it, modify the system prompts, tune it to your taste — the architecture is simple enough that you can reshape it without fighting a framework.

If you try it on something interesting, I'd love to hear what worked and what broke. The most useful feedback so far has been about the termination criterion — the Planner's GOAL COMPLETE call is fuzzy, and there's a more principled version hiding somewhere in there.
